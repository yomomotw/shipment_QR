# 07 測試

## 原則

- 每個任務的驗收條件都要有對應的自動化測試，除了明確標示由使用者執行的實機測試。
- 回報「完成」前要實際執行測試並附上結果。沒跑過的不可說通過。
- 測試用獨立的暫存資料庫，不可動到 `data/app.db`。
- 寄信在測試中用假的寄信器攔截，不可真的寄出。

## 測試分層

| 層 | 工具 | 涵蓋 |
|---|---|---|
| 單元 | pytest | `services/` 內的純邏輯：序號解析、保固計算、QR 文字、狀態機 |
| 路由 | pytest + httpx | 權限、表單驗證、公開頁不洩漏資料 |
| 端對端 | Playwright | 建檔到列印、QR 解碼比對、手機尺寸的報修流程 |

QR 解碼比對的做法：Playwright 對標籤上的 QR 截圖，用 OpenCV 的 `QRCodeDetector` 解碼，與 `device.qr_payload` 比對是否逐字相同。現有的純前端版就是這樣驗證的。

## 必測案例

### 序號解析（P1-04）

| 輸入 | 預期 |
|---|---|
| `SN0001~SN0003` | `SN0001`、`SN0002`、`SN0003` |
| `SN0098~SN0101` | 四個，補零維持四位數 |
| `A1,A2\nA3；A4` | 四個（逗號、換行、全形分號都是分隔） |
| `SN0005~SN0001` | 錯誤：迄號小於起號 |
| `SN0001~AB0003` | 錯誤：前後前綴不一致 |
| `A1,A1` | 錯誤：序號重複，並指出 `A1` |
| 3 個序號，數量填 4 | 錯誤：數量不符 |
| 與台帳既有序號重複 | 錯誤，列出重複的序號，整批不建立 |
| 頭尾與中間的空白、空行 | 忽略 |

### 保固（P1-04）

| 情境 | 預期 |
|---|---|
| 開始日 2026-11-16，12 個月 | 到期日 2027-11-16 |
| 開始日 2026-01-31，1 個月 | 到期日 2026-02-28（月底對齊，不可變成 3 月） |
| 開始日留空 | 帶入出貨日期 |
| 今天 = 到期日 | 在保 |
| 今天 = 到期日後一天 | 過保 |

「到期日當天算在保」是暫定規則，見 `08-decisions.md` Q-02。

### QR 文字（P1-05）

| 情境 | 預期 |
|---|---|
| 未勾選任何欄位，無對外網址 | 只有型號、序號、叫修電話三行 |
| 勾選規格與出貨日期，有對外網址 | 與 `04-qr-label-spec.md` 的範例逐字相同 |
| 勾選規格但規格為空 | 不輸出 `規格:` 行 |
| 規格頭尾有空白行 | 去除頭尾空白行，中間的行不變 |
| 對外網址結尾有 `/` | 組出的網址沒有 `//` |
| 有對外網址 | `線上報修` 是最後一行，結尾沒有換行 |
| 型號含中文 | QR 編碼後解碼，與原文逐字相同 |
| 產生 1,000 個 scan_code | 全部 8 碼、字元都在允許集合內、無重複 |

### 標籤（P1-07）

- 標籤表格的列數等於 3，標題依序為序號、型號、叫修電話。
- 標籤 DOM 內不含出貨日期、訂單號、規格的文字。
- 12 台設備各自的 QR 解碼後，序號行各不相同且對應正確。
- 修改設備型號後補印，QR 解碼結果仍是原本的 `qr_payload`。
- 60×40 與 50×30 兩種尺寸下，表格文字沒有超出邊框。

### 公開頁（P1-08、P2-02）

- 未勾選 `int_po` 的設備，公開頁的 HTML 原始碼中搜尋不到內部訂單編號。
- 公開頁的 HTML 原始碼中搜尋不到客戶名稱。
- 不存在的 `scan_code` 與格式錯誤的 `scan_code` 回應相同。
- 問題描述填入 `<script>alert(1)</script>`，後台顯示時是純文字。
- 同一設備一小時內第 4 次報修被擋。

### 工單狀態機（P2-01）

- 轉換表內每一列各一個測試。
- 表外的轉換（例如 `new → completed`、`closed → in_progress`）被拒。
- 工程師對不是指派給自己的工單做轉換被拒。
- `quote_status = pending` 時，`accepted → in_progress` 被拒。
- 同一設備已有未結案工單時，建立第二張被拒。

### 通知（P2-04、P3-05）

- 寄信器丟出例外時，建立工單的請求仍回成功，`notification_log` 有一筆 `failed`。
- 未受理提醒對同一張工單只寄一次。
